# Accessibility Audit — WCAG 2.1 AA

**Date:** 2026-09-08 · **Scope:** Landing/Optimizer flow, Roster, Teams, Plan, `src/index.css`, `tailwind.config.js`
**Method:** Static code review only (no dev server, no live AT testing).
**Baseline:** PR #118 (placeholder contrast, ER validation, describedby, bullets) is already merged — findings below were checked against current code, not memory of that PR.

## Summary

**Issues found:** 6 (1 finding class, 6 occurrences) | **Critical:** 0 | **Major:** 1 (5 occurrences) | **Minor:** 1 (1 occurrence)

The codebase is unusually disciplined about accessibility already — skip link, single persistent live-region pattern for panel-level notices (`App.tsx`, `ImportPanel.tsx`, `ExplainBuild.tsx`, `Results.tsx` share outcome, `OptimizePanel.tsx` search progress), `aria-disabled` + early-return instead of `disabled` everywhere focus-preservation matters, roving-tabindex `Segmented`, a hand-rolled `Combobox` with correct `aria-activedescendant`/scroll-into-view/listbox semantics, decorative SVGs correctly `aria-hidden`, colour never used as the only channel (element hues, grade markers, met/unmet checkmarks), and documented contrast math in code comments (e.g. `field` placeholder opacity, `element.*` tokens). No contrast failures, no keyboard traps, no missing form labels, and no stray `div`/`span` click handlers were found anywhere in the reviewed tree.

The one substantive issue is a **live-region mounting anti-pattern** that the codebase's own comments (see `App.tsx:305-308`, `ImportPanel.tsx:309-311`, `ExplainBuild.tsx:54-56`, `Results.tsx:442-445`) correctly identify and fix for panel-level notices, but which recurs in five inline/local error and status messages that were not brought under the same pattern.

## Finding 1 — Freshly-mounted `role="alert"`/`role="status"` nodes are not reliably announced

**WCAG:** 4.1.3 Status Messages (AA) — also touches 3.3.1 Error Identification (A), since the visual text is correct but may not reach screen-reader users at all.
**Severity:** 🟡 Major

### The bug, in the codebase's own words

The team already diagnosed this exact failure mode and left it in comments at four call sites:

> "A region mounted in the same commit as its text is not yet observed, so nothing is announced" — `App.tsx:305-308`
> "The status lives in a persistent region — a role="status" node created in the same commit as its text announces nothing" — `ImportPanel.tsx:200-202`
> "Persistent live regions: announcing only works if the container is already in the DOM when its text arrives" — `ExplainBuild.tsx:54-56`
> "A live region that doesn't exist when its text arrives announces nothing" — `Results.tsx:442-445`

Each of those four files fixes it correctly: an always-mounted `<p className="sr-only" role="status">`/`role="alert"` whose _text content_ changes, with the visible, styled `Callout` rendered separately and carrying no role of its own.

Five other messages in the same codebase do **not** follow this pattern — the `role="alert"`/`role="status"` element itself is the thing that gets conditionally mounted, already containing its final text in the same commit. This is inconsistent across browser/AT combinations (Firefox+NVDA generally catch a freshly-inserted `alert` node; Chrome+JAWS and Chrome+VoiceOver frequently do not, because the accessibility tree insertion and the "new live region" notification aren't guaranteed to be treated as a announceable mutation the same way a text-content change inside an existing node is).

### Occurrences

| #   | File:Line                                               | What's freshly mounted                                                                                                                                                                                                                                                                                             |
| --- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | `src/components/ArtifactForm.tsx:175-177`               | `<p id="level-error" role="alert">{levelError}</p>` — swapped in for the `level-hint` `<p>` (no role) only once `levelError` is set. A screen-reader user tabbing past Level after a bad entry may hear nothing.                                                                                                   |
| 2   | `src/components/ArtifactForm.tsx:195-199`               | `{error && error !== levelError && (<Callout tone="error" role="alert">{error}</Callout>)}` — the submit-time validation banner. Mounts fresh on failed submit.                                                                                                                                                    |
| 3   | `src/components/OptimizePanel.tsx:442-449`              | The Minimum ER field's `<p id={...} role="alert">Enter a positive number…</p>` is swapped in for the (role-less) hint `<p>` only when `minERInvalid` — identical pattern to #1.                                                                                                                                    |
| 4   | `src/components/Results.tsx:242-263` (role at line 248) | `if (result.status === 'infeasible') return (<Callout tone="error" role="status">…</Callout>)` — the whole "No build satisfies all constraints" panel is a fresh subtree each time a run comes back infeasible; there is no persistent region backing it (unlike the share-outcome region lower in the same file). |
| 5   | `src/plan/PlanView.tsx:309-313`                         | `{failed && (<Callout tone="error" role="alert">Building the plan failed — please try again.</Callout>)}` — fresh mount on failure.                                                                                                                                                                                |

A sixth, lower-risk instance: `src/plan/PlanView.tsx:292-293`, `<div role="status" aria-live="polite">` wrapping the "Optimising member N of 8…" progress text, is also conditionally mounted (`{running && (...)}`) rather than persistent. Explicitly setting `aria-live="polite"` at mount time is a bit more AT-friendly than a bare `role="status"` with no `aria-live`, but it is still the same class of risk as #1-5, since some AT/browser combinations only start observing a live region after it has existed for one paint.

### Fix

Apply the same fix already used for the panel-level notices in `App.tsx` / `ImportPanel.tsx` / `ExplainBuild.tsx` / `Results.tsx`'s share outcome: keep one always-mounted `sr-only` `role="alert"`/`role="status"` element per message slot, and let its **text content** (not its presence) change. The visible `Callout`/`<p>` stays exactly as it is today (still conditionally mounted, still carrying no role), it just stops being the only carrier of the announcement. Concretely:

- ArtifactForm: add a persistent `<p id="level-error" role="alert" className="sr-only">{levelError ?? ''}</p>` (or fold it into the panel's existing pattern), and drop `role="alert"` from the visible hint/error swap at line 175. Same treatment for the top-level `error` Callout at line 196.
- OptimizePanel: same treatment for the ER field's error/hint swap at 442-449.
- Results.tsx: add a persistent `role="status"` region for the infeasible case (or reuse the existing one at line 446 if its lifetime can be extended to cover this branch too — note the current one is scoped to `share`, so this needs its own).
- PlanView.tsx: add a persistent region for `failed`, and consider doing the same for the `running` progress text at line 292-293 for consistency (lower priority — `aria-live="polite"` on mount is a smaller version of the same risk).
