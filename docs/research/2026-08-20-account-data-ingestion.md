# Genshin Impact account data ingestion: options for rpg-build-optimizer

## 1. Enka.Network API

**What it is**: A free, no-auth-required read-only API that scrapes a player's in-game **Character Showcase** (the profile card feature) by UID, and mirrors the raw game-client data structure.

- **Endpoint**: `GET https://enka.network/api/uid/{UID}/` (full data) or `.../{UID}/?info` (player info only). [API-docs](https://github.com/EnkaNetwork/API-docs/blob/master/api.md)
- **Coverage**: Only characters the player has explicitly placed in their **Character Showcase** — capped at **8 slots originally, raised to 12** in a later game update. It is _not_ the player's full roster; anyone who hasn't showcased a character (or has an empty/hidden showcase) returns nothing for them.
- **Per-character detail is actually rich**: `avatarInfoList` includes `fightPropMap` (50+ computed combat stats), `skillLevelMap` (talent levels), `talentIdList` (constellations unlocked), and `equipList` containing weapon (`weaponStats`) and artifacts with **`reliquaryMainstat` and `reliquarySubstats` (substat ID + rolled value)** — i.e., full artifact detail _for showcased characters only_.
- **Auth**: None. Just requires a custom `User-Agent` header (Enka asks for this so they can identify/support integrations).
- **Rate limits & caching**: Dynamic, undocumented exact numbers, but every UID response includes a `ttl` field = seconds until Enka will re-scrape that UID's showcase. Repeated polling inside the `ttl` window still burns rate-limit budget even though it serves cached data (hit it too fast → slowed responses / HTTP 429). Enka's own guidance is to cache client-side keyed on `ttl`, ideally in Redis. [Status page](https://status.enka.network/)
- **ToS risk**: Low — Enka is a well-established, widely-used community service (used by Genshin Optimizer, akasha.cv, and many Discord bots) and only reads public showcase data miHoYo already exposes client-side. No account credentials touch it.
- **Reliability**: Generally solid uptime; community-run, breaks briefly on new-character patch days until they push updated character data, has a public status page.
- **Libraries**: [`enka-network-api` (npm/JS)](https://www.npmjs.com/package/enka-network-api), [`enka` (Python)](https://pypi.org/project/enka/), [`enka-network-api` (Java)](https://enka-docs.kazury.me/api/getting-started), Go wrapper, etc.

## 2. HoYoLAB / miHoYo game-record API (unofficial, cookie-based)

**What it is**: The private API HoYoLAB's own website/app uses (`api-os-takumi.mihoyo.com` / Miyoushe equivalent for CN) to power features like the "Genshin Impact" tab, Battle Chronicle, Spiral Abyss records, etc. Not documented or published by miHoYo/HoYoverse — reverse-engineered by the community.

- **Coverage**: This is the one source that returns the player's **entire owned character roster**, not just a showcase — including equipped weapon and **artifacts with substats**, talent levels, and constellations for every character (via a "character detail" call that takes the roster's avatar IDs and returns full equip data). It also exposes Spiral Abyss history, wish/gacha history (needs a separate short-lived `authkey`, not the login cookie), and real-time notes (resin, expeditions, etc).
- **Auth**: Requires the user's **HoYoLAB session cookie** (`ltuid_v2`/`ltoken_v2`, or `stoken`/`cookie_token` for some endpoints). Getting this cookie means asking the user to log into HoYoLAB in a browser and copy cookie values out of dev tools, or (riskier) email+password login flows some wrapper tools implement directly. This is real friction and is a UX/trust hurdle — you are asking users to hand you session credentials for their HoYoverse account.
- **Risk**: This is the material risk in the whole landscape. These cookies are powerful — community docs and disclaimers note that a leaked/misused cookie can be used to **change the account password, spend Genesis Crystals, purchase items, or initiate account transfers/refunds**, not just read data. Auto-login/wrapper tool authors explicitly disclaim responsibility for account safety. HoYoverse's public ToS bans "any plug-in, booster or other third-party tool that disrupts fair gameplay," with penalties ranging from reward removal to permanent bans, though enforcement historically has targeted gameplay-automation/cheat tools, not read-only stat trackers — genshin.py-based bots (Hoyo Buddy, etc.) have operated for years without mass bans, but there's no official guarantee and no published rate limits, so it remains a ToS gray area, not a sanctioned integration.
- **Reliability**: Undocumented, unversioned endpoints that miHoYo can change without notice; wrapper maintainers patch reactively. There is periodic geetest/captcha friction on login for some accounts/regions.
- **Libraries**: [`genshin.py`](https://github.com/seriaati/genshin.py) (Python, actively maintained fork of the original `genshinstats`, async/pydantic-based, the de facto standard), [`hoyolab-api`](https://github.com/vermaysha/hoyolab-api) (unofficial JS/TS wrapper — closer to this project's likely stack), plus various Discord-bot projects (Hoyo Buddy) built on genshin.py that show it in production use.
- **No official API/developer program exists.** Searches turned up no miHoYo/HoYoverse announcement of a public Genshin developer API as of 2026 — everything in this category remains unofficial and reverse-engineered.

## 3. GOOD format (Genshin Open Object Description)

**What it is**: A community-standard JSON interchange schema, defined and maintained inside the [frzyc/genshin-optimizer](https://github.com/frzyc/genshin-optimizer) monorepo as the [`gi-good` library](https://github.com/frzyc/genshin-optimizer/blob/master/libs/gi/good) ("an Interface for the Genshin Open Object Description... an import format for Genshin scanners"). It is the de facto lingua franca of the Genshin optimizer/scanner ecosystem — effectively every third-party scanner and optimizer either emits or consumes it.

- **Contents**: format/version header, `characters[]` (level, ascension, constellation, talent levels), `weapons[]` (level, refinement, ascension, location), `artifacts[]` (set, slot, level, rarity, main stat, **full substats with values**), and `materials[]` (inventory counts of development mats).
- **How users produce it**: Not obtained from any API — it's generated locally by scanning the player's own PC game client with OCR-based desktop tools (see #4), or hand-authored/exported by tools that already hold the data. It's a _file format_, not a live data source.
- **Fit for this project**: A GOOD import feature is the standard "power user" on-ramp — if this project wants to support serious optimization without owning a scanner, accepting GOOD-file upload as one ingestion path costs little and taps into an existing tool ecosystem.

## 4. Scanners (Inventory Kamera, GOODScanner/GOODCapture, Android scanners)

- **[Inventory Kamera](https://github.com/Andrewthe13th/Inventory_Kamera)** (Windows only): reads pixels from the live game window via OCR, scanning characters, weapons, artifacts, and materials, and exports a GOOD JSON file. Requires the desktop game client running locally, VC++ redistributable, and a manual scan pass (pointing the tool at each inventory screen) — meaningful setup friction, but produces a complete, exact inventory (every artifact you own, not just equipped/showcased ones). Actively forked/maintained (multiple community forks exist, including ultrawide-monitor variants), and it auto-updates its character-data tables each patch.
- **[genshin-inventory-scanner-android](https://github.com/steve1316/genshin-inventory-scanner-android)**: same idea, OCR against the mobile client, also GOOD-format output. Mobile OCR scanning is inherently less reliable and slower than PC.
- **Platform limits**: all scanners are PC(-window)/mobile-screen dependent, single-player-run-locally tools — they cannot be embedded server-side or run for a user remotely; the user must install and run them themselves, then upload the resulting GOOD file. This makes scanners strictly an "advanced/optional" ingestion path, never an MVP-friendly one.
- **Maintenance status (2026)**: still alive and patched by community maintainers as of this research, but scanner tools as a category have historically had bursts of inactivity between maintainers/game engine changes; treat any single scanner repo as a "best effort" dependency, not a guaranteed-available service.

## 5. Newer/official options (2025–2026)

- No official miHoYo/HoYoverse public API or developer program was found as of this research (mid-2026) — this remains an entirely unofficial-tooling landscape, same as in prior years.
- **akasha.cv** (Genshin damage-leaderboard site, arguably the closest comparable "endgame optimization" product to this project) does **not** have its own independent data-collection pipeline — it explicitly ingests from **Enka's showcase API** (confirmed: "akasha.cv uses Enka's API... the developer of akasha.cv changes their API very frequently," and Akasha itself runs an [Enka-linked showcase profile](https://enka.network/u/808527727/)). Its own public API (wrapped by [`akasha-py`](https://github.com/seriaati/akasha-py)) is undocumented and changes without notice — not something to build critical-path ingestion on.
- **frzyc/genshin-optimizer**, the most feature-complete open-source optimizer, supports **all four ingestion paths simultaneously**: GOOD JSON upload, GOODScanner/GOODCapture scanner import, **Enka UID lookup**, and **HoYoLAB/Miyoushe cookie import** (cookie provided by the user). This is strong direct evidence for how the most mature comparable product resolves the exact tension this research was asked to settle: it doesn't pick one — it layers cheap/partial (Enka) with optional/complete (HoYoLAB cookie, or scanner+GOOD for the most dedicated users).

## Recommendation

**For the MVP**: Use **Enka.Network** as the primary, zero-friction ingestion path (UID → showcase characters with full artifact substats). This lets a user go from "nothing" to "seeing optimizer output" in seconds with no login, matches what akasha.cv itself relies on, and carries no account-security risk. Accept its core limitation up front in the product (only 8–12 showcased characters) — for an MVP that's a reasonable scope-limiter, not a blocker, since it's still enough to demo/validate the optimizer and recommendation logic on a user's best characters.

Pair Enka with a **GOOD-file upload** option from day one (cheap to add: it's "just" a JSON schema to parse) — this immediately unlocks the power-user segment who already run Inventory Kamera or similar for other tools, without this project needing to build or maintain a scanner itself.

**For the full product**: Add **HoYoLAB cookie import (via genshin.py-equivalent logic, or the JS `hoyolab-api` wrapper)** as an explicit, clearly-labeled opt-in "connect full account" feature once the product needs full-roster optimization (i.e., once you're recommending swaps across a user's _entire_ barely-showcased roster, not just their showcased favorites). Treat this as a trust-sensitive feature: be explicit with users about what the cookie can do, store it encrypted, never log it, and give users an easy disconnect/revoke path — the same caution the existing wrapper ecosystem (Hoyo Buddy, genshin.py) already documents for its own users. Do not attempt to build or bundle an OCR scanner yourselves; if deeper inventory completeness is wanted beyond what HoYoLAB's character-detail endpoint gives, integrate with the existing GOOD ecosystem (accept scanner output) rather than reinventing OCR scanning.

In short: **Enka for the low-friction default, GOOD-file import for power users on day one, HoYoLAB cookie import as an opt-in upgrade once full-roster coverage is a real product requirement** — mirroring exactly what frzyc/genshin-optimizer, the most mature comparable app, already does by supporting all of these simultaneously rather than picking one.
