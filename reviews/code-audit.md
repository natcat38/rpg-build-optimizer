# Code Audit — 2026-08-28

Scope: full `src/` tree (85 non-test files, 56 test files, ~40k lines incl. generated data). Method: FILE-MAP/CONTEXT orientation, `git ls-files | wc -l` sizing, `ts-prune` unused-export scan, targeted reads of the largest/critical modules (optimizer/search.ts, App.tsx, share/url.ts, game/registry.ts, benchmark.ts). Overall impression: mature, deliberately-scoped codebase — ADRs already document and reject several abstractions this kind of audit usually flags (e.g. ADR-0012 collapsed a `GameAdapter` interface to a concrete adapter for YAGNI). Findings below are the residual, real issues.

## Ranked findings

1. **Dead export with a stale doc comment** — `src/optimizer/benchmark.ts:17` `formatReduction()`. Its TSDoc claims it's "used by ... the browser hero demo (`src/components/App.tsx`)", but `App.tsx` has no reference to it (confirmed via grep and `ts-prune`, which flags it as fully unused). Either the hero demo regressed to not use shared formatting (worth checking for a duplicated inline formatter in `App.tsx`) or the export + comment are dead. **Action:** grep `App.tsx` for its own reduction-formatting logic; if duplicated, wire it to the shared helper; if truly obsolete, delete the export and comment.

2. **Main bundle is a single 561 KB chunk with no code-splitting** — `dist/assets/index-*.js` (production build already present in repo, gitignored). `App.tsx` statically imports `PlanView`, `TeamsView`, `RosterView`/`CharacterDetail`, `ImportPanel`, `ExplainBuild`, etc. — all feature panels ship in the initial chunk even though a player typically starts on one view. **Action:** `React.lazy`/`Suspense` around the heavier, not-immediately-visible panels (Plan, Teams, Roster drawer) to shrink first-paint JS.

3. **`data.generated.json` (328 KB, 16.7k lines) is duplicated across bundles** — imported by `src/game/genshin/adapter.ts:18` (`import rawData from './data.generated.json'`), which is pulled in by both the main thread (`optimizer/context.ts`, `App.tsx`, etc.) and the worker entry (`src/workers/*` → `optimizer/context.ts` → `adapter.ts`). Vite builds the worker as a separate bundle, so the full reference dataset is serialized twice (561 KB main + 143 KB worker, largely the same JSON). **Action:** consider sourcing the dataset once (e.g. `fetch` + cache, or `structuredClone`/postMessage the parsed object into the worker at startup) if bundle size becomes a concern; low urgency since it's static/cacheable, but worth a comment in ADR-0002 or a follow-up ADR if intentional.

4. **`App.tsx` is a 710-line grab-bag module** — `src/components/App.tsx` defines `Section`, `ThesisHero`, `SolvedHero`, `useScrollSpy`, `SharedBuildBanner`, and the top-level `App` all in one file (lines 51, 98, 115, 176, 224, 250). None of these are exported elsewhere, so it's not dead code, but it mixes marketing/landing concerns (hero sections, scroll-spy) with the app shell in a single module. **Action:** split hero/landing pieces into `src/components/landing/` (or similar) to keep `App.tsx` to routing/state wiring; low risk, purely organizational.

5. **`src/teams/comps.ts` (1097 lines) and `src/meta/teammates.ts` (751 lines) are large curated-data modules** — both are hand-authored game data tables (comp archetypes, teammate synergy), not logic-dense code, so size alone isn't a defect, but they have no companion `*.data.ts`/`*.curated.ts` split from validation logic the way `damage/setBonuses.ts` does (which separates the 410-line curated table from `setBonuses.test.ts`). **Action:** low priority — only worth splitting if these files are edited often enough that the mixed data+logic makes diffs noisy; otherwise leave as-is (each patch-refresh runbook already targets specific line ranges).

6. **Unused exports flagged as "only used in module"** — `ts-prune` lists ~25 types/consts (`SearchProgressSnapshot`, `FourPieceBonus`, `HIT_KINDS`, `EnemyConfig`, `GameId`, `GAMES`, `SearchOptions`, `BuildSnapshot`, etc.) exported but referenced only within their own file. These are almost all intentional public API surface for a module (types consumed by tests via type-only imports, or documented seams like `game/registry.ts`'s `GameId`/`GAMES` which ADR-0008/0012 explicitly keep as a single-entry extensibility point). No action needed — false positives from `ts-prune`'s module-boundary heuristic, but worth noting so a future contributor doesn't "clean up" `game/registry.ts` and break the documented seam.

7. **Coverage gaps look thin at the edges, not the core** — the three critical paths called out in the task (optimizer pruning `search.ts`/`search.test.ts` 733/631 lines, share encode/decode `share/url.ts`/`url.test.ts` 287/538 lines, GOOD import `import/good.ts`/`good.test.ts` 234/416 lines) all have proportionally larger test files than implementation files — good sign, no action needed there. Smaller peripheral modules (`src/ui/scrollIntoView`-style helpers, `src/invest/obtainability.ts`) have thinner or no dedicated tests, but they're low-complexity/low-risk. **Action:** none urgent; if adding tests, prioritize `damage/formula.ts`'s `additiveBase` (flagged unused-outside-module by `ts-prune` — verify it's actually exercised by `formula.test.ts` via the public formula function, not dead).

## Non-findings worth noting

- No stale/orphaned files, no committed build artifacts, no TODO/FIXME backlog in `src/`.
- The `GameAdapter` interface → concrete adapter collapse (ADR-0012) and the `game/registry.ts` seam are both already-considered, documented YAGNI decisions — not re-flagging them as over-engineering.
- Worker boundary (`src/workers/`) is small and single-purpose (protocol + client + entry), with a documented synchronous fallback — no coupling concerns found.
